### 1. INTRODUCTION
NOTE Avant de lire le présent guide, nous vous recommandons de lire le document Renseignements généraux sur l’adaptation des SEV (SW-76). Il vous donnera un aperçu des spécifications nécessaires pour rendre un système d’enregistrement des ventes (SEV) conforme aux mesures sur la facturation obligatoire afin de permettre aux exploitants visés par ces mesures de respecter leurs obligations. Le document SW-76 comprend aussi une partie présentant les termes les plus couramment utilisés dans le présent guide.
1.1 À qui s’adresse ce guide?
Ce guide s’adresse à vous si vousavez développé ou avez l’intention de développer unsystème d’enregistrement des ventes (SEV). Il n’explique pas comment développer un nouveau SEV; il décrit seulement les spécifications nécessaires pour rendre un SEV conforme aux nouvelles mesures sur la facturation obligatoire. En effet, votre SEV doit être compatible avec l’environnement technologique mis en place (appelé MEV-WEB) pour permettre à tout exploitant visé par les mesures de respecter ses obligations.
Le MEV-WEB, hébergé dans un environnement infonuagique, est accessible par voietélématique. Pour communiquer avec le MEV-WEB, votre SEV doit être développé en respectant le protocole de communication défini dans le présent guide et avoir obtenu notre certification.
Pour obtenir plus de renseignements concernant la certification des SEV, veuillez consulter les documents suivants :
• Cas d’essais pour les concepteurs de SEV (SW-77) • Cas d’essais pour les concepteurs de SEV – Déclaration de conformité (SW-78) • Démarche pour l’obtention d’une certification (SW-79)
Vous pouvez aussi consulter la section Partenaires de notre site Internet à revenuquebec.ca.

1.2 Contenu du guide
Ce guide présente les exigences logicielles et les spécifications relatives au protocole de communication applicables à votre SEV pour assurer sa compatibilité avec le MEV-WEB. Il explique et illustre notamment les adaptations nécessaires. Les exigences sont accompagnées d’exemples, de mises en situation et de gabarits de documents. De plus, des tableaux et des schémas ont été ajoutés pour apporter des précisions supplémentaires et illustrer les différents concepts.
En plus de ce guide, les documents complémentaires suivants sont également disponibles :
• Listes de contrôle(SW-73.1): Résumé du présent guide et tests pour vérifier le bon fonctionnement de votre SEV. • Messages d’erreur(SW-73.A): Liste des messages d’erreur transmis par le MEV-WEB. • Exemples de documents transactionnels (SW-73.B) : Exemples de documents transactionnels, de requêtes et de code source en langage Java (Android). • Exemple de code source (SW-73.C) : Exemple de code source en langage C# qui fonctionne avec le Microsoft .NET Framework 4.8.

2.2 Topologies : Appareils et MEV-WEB
Tableau 3 : Type d'appareil Les topologies présentées ci-dessous sont des combinaisons de connectivité les plus communes entre des appareils et le MEV WEB.
Une attention particulière doit être apportée à la définition différenciant un appareil d’un terminal.
Un appareil hôte a la possibilité de communiquer avec le MEV-WEB. Chacun des appareils devant interagir avec le MEV-WEB ou produire des factures, des notes de crédit ou des documents doit être doté d’un certificat signé par le MEV-WEB. Les tâches précédemment mentionnées sont strictement réservées aux appareils et incidemment exclues des fonctions d’un terminal.
Un terminal est un appareil satellite connecté à un appareil de point de vente hôte (appareil hôte) avec lequel il interagit. L'appareil hôte contrôle soit le terminal lui-même, soit ses tâches. Un terminal peut être mobile, offrant une liberté de mouvement à l’utilisateur, ou fixe, et disposé stratégiquement dans l'établissement. Il est destiné à être utilisé exclusivement par l’exploitant ou ses employés pour saisir de nouvelles commandes, modifier des additions existantes et commander à l'appareil hôte la production de documents (par exemple, une addition ou une note de crédit). Plusieurs terminaux peuvent être connectés à un même appareil hôte.

2.2.1 Identification
Chaque appareil doit posséder un identifiant unique (propriété IDAPPRL), généré par le MEV-WEB à la suite d’une requête de signature de certificat (Certificate Signature Request [CSR]). L’identifiant pour un terminal est obtenu par l’appareil hôte auquel il est connecté, et identifie le terminal pour lequel l'appareil hôte réalise ses tâches. Un identifiant est attribué à vie.
2.2.2 Journalisation
Les actions effectuées sur un terminal doivent être journalisées soit dans le terminal, soit dans l'appareil hôte avec lequel il interagit. Ce qui doit être journalisé varie selon l’utilisateur. À la demande de l’exploitant, l’exportation des données de journalisation d’un appareil hôte doit inclure celles de tous ses terminaux.
Tableau 4 : Journalisation selon l’utilisateur
La journalisation partielle exclut toutes les actions effectuées avant qu'une facture soit produite : ajout ou retraitd’items, modification des quantités ou des prix, annulation avant impression.
2.2.3 Conclure une transaction
Les actions initiées par un terminal basic sont complétées par l’appareil hôte. Le SEV utilise l’identifiant du terminal pour produire la transaction.

3.1.1 Données transactionnelles des exploitants
Chaque exploitant visé par les mesures doit transmettre les renseignements prescrits au MEV-WEB au moyen d’un SEV certifié, soit un SEV compatible avec le MEV-WEB et qui respectenos exigences d’opération.
3.1.2 Compte utilisateur
Le compte utilisateur caractérise un ensemble de ressources informationnelles attribuées à l’utilisateur d’un appareil comme un SEV.
Votre SEV peut gérer les comptes utilisateurs, soit les comptes employés ou celui de l’exploitant. Il doit créer un compte utilisateur par employé sauf s'il n'identifie pas les employés, car certains secteurs d'activité peuvent amener d'autres directives spécifiques.
Par ailleurs, si plusieurs exploitants manipulent le même SEV, ils doivent tous posséder leur propre compte utilisateur sécurisé. Pour le secteur du transport rémunéré de personnes, tous les employés doivent également posséder leur propre compte utilisateur. Dans ce cas, ce sont les exploitants qui ont la responsabilité de créer ces comptes pour leurs employés. Par conséquent, si vous voulez que votre SEV puisse être utilisé dans tous les secteurs d’activité, il doit permettre aux exploitants de créer un compte utilisateur pour chaque employé selon les spécifications mentionnées dans ce guide.
Chaque utilisateur en utilisant son compte utilisateur doit pouvoir produire des factures personnalisées, des renseignements obligatoires, tels que le nom de l’utilisateur, le nom, le numéro d’inscription au fichier de la TPS et le numéro d’inscription au fichier de la TVQ de l’exploitantassociésont exigés pour créer un compte. Ensuite, l’exploitant doit faire valider les informations par le MEV-WEB en lui faisant parvenir une requête de type « utilisateur » pour finaliser la création du compte.
NOTE Si les données des utilisateurs sont créées à partir d’un serveur distant, l’administrateur du serveur peut effectuer une requête de type «utilisateur » lui permettant de validerles informations de chaque utilisateur.
Dans le secteur du transport rémunéré de personnes, les transactions effectuées par un utilisateur doivent être seulement accessibles par cet utilisateur ou par l’exploitant responsable de la remise des taxes de ses employés. À cet effet, l’exploitant doit avoir accès aux données de ses employés, mais il ne doit pas avoir accès aux données d’un autre exploitant. Pour les autres secteurs, les transactions effectuées par un employé peuvent être accessibles par tous lesemployésd’un mêmeexploitantet parl’exploitantlui-même. 3.7.5 Mécanismes de sécurité
3.7.5.1 Authentification par certificats
Pour chaque requête effectuée, la communication doit être sécurisée au moyen du protocole TLS avec suite cryptographique autorisée (voir la partie 3.7.4). Un certificat numérique est un document qui contient plusieurs informations, dont une clé publique, mais aussi des informations permettant d’identifier son propriétaire. Dans le cadre des mesures sur la facturation obligatoire, le certificat numérique doit notamment contenir un numéro d’identification.

3.7.5.3 Format des signatures numériques
Une signature numérique est un mécanisme qui permet de garantir l’intégrité d’un document électronique et d’en authentifier l’auteur.
Pour réaliser une signature numérique, votre SEV doit produire une empreinte numérique des renseignements relatifs au document en utilisant l’algorithme de hachageSHA-256. Cette empreinte sert à valider l’intégrité des données et à garantir qu’elles n’ont pas été altérées.
Une fois l’empreinte numérique réalisée, l’empreinte doit être signée avec la clé privée incluse dans le certificat de l’exploitant. La clé privée doit utiliser l’algorithme de chiffrement ECDSA_P256 avec une longueur de clé de 256 bits.

Les champs versi et VERSI doivent correspondre à la version du SEV actuellement utilisée, alors que les champsversiParnetVERSIPARNdoivent correspondre à la version parent, c’est-à-dire la version précédente (par exemple, la version « 1.0 » est la version parent de la version « 1.1 »).
Notez que les versions indiquées dans la structure JSON (versi etversiParn) doivent toujours être déterminées par le SEV, alors que les versions indiquées dans l’en-têtepeuvent être déterminées par un SEV ou un serveur distant, selon l’appareil qui initialise la requête au MEV-WEB.

4.4.1.1.11 Commerce électronique
Le commerce électronique se définit par l'utilisation de moyens numériques de communication en vue de vendre des biens et des services sur un site Internet ou sur une plateforme numérique, ce qui inclut un paiement (ou toute autre forme de compensation) et une livraison physique ou numérique.
Dans le cadre des mesures sur la facturation obligatoire, le champ commerElectr sert à identifier les ventes réalisées en commerce électronique. Ce champ doit avoir la valeur « O » (Oui) si l’appareil utilisé pour payer la transaction appartient au client et que ce dernier effectue le paiement à partir de votre logiciel (application mobile ou page Web).
Par exemple, un paiement Exemple 17 : Commerce électronique
effectué sur un site Web, à partir d’un ordinateur personnel ou à partir d’une application mobile sur un téléphone intelligent ou sur une tablette, est considéré comme du commerce électronique.
Cependant, si une borne de commandes dans un établissement de restauration est utilisée, et donc que l’appareil n’est pas la propriété du client, alors ce n’est pas considéré comme du commerce électronique, même si le moyen de paiement est sans contact. Dans ce cas, le champ commerElectr doit avoir la valeur « N » (Non).

4.4.1.1.13 Mode de paiement
Le champ modPai précise le mode de paiement utilisé pour payer la facture ou indique que le montant n’est pas payé (ex. : addition, montant porté au compte du client ou client parti sans payer). Ainsi, lors de la production d’une soumission, d’une estimation, d’une addition ou si une transaction est annulée en cours de saisie, ce champ doit avoir la valeur « SOB » (sans objet).
Si le mode de paiement sélectionné ne figure pas parmi les choix proposés ou si une commande est faite par une plateforme numérique et quel’exploitant qui produit la facture ne connaît pas le mode de paiement utilisé par le client, le champ devrait avoir la valeur « AUT » (autre). Dans l’éventualité où plus d’un mode de paiement serait utilisé, le champ devrait avoir la valeur« MIX » (mixte), indiquant une combinaison de plusieurs modes de paiement.
Le champ devrait avoir la valeur « INC » (mode de paiement inconnu) seulement pour le secteur d’activité de la restauration, dans un établissement de restauration où sont offertes des boissons alcooliques en vertu d’un permis de bar et lorsqu’une boisson est servie sans aliment et que le reçu de fermeture est produit avantque le mode de paiement soit connu.
Par ailleurs, si votre SEV offre une fonction d’arrondissement à cinq cents près lors de paiements en argent comptant, le mode de paiement devrait avoir la valeur « ARG » ou «MIX ».
NOTE Voyez lapartie3.4pour obtenir plus de précisions sur les effets du retrait de la pièce d’un cent sur le fonctionnement du SEV.
Si une transaction est conclue avant que le paiement soit reçu dans le cadre d’un contrat pour un compte client, la valeur « PAC » (porté au compte) peut être attribuée. Dans cette situation, la mention « PORTÉ AU COMPTE » doit figurer au-dessus du code QR. Comme tous les autres modes de paiement, ce mode mène à la production d’un reçu de fermeture.
Si aucun paiement n’est effectué après la production d’une facture originale ou d’une facture révisée (par exemple, l’exploitantoffre unbiengratuitementau client ou le client est parti sans payer), une transaction de type « RFER » doit être transmise avec tous les renseignements prescrits. La valeur du champ modPai doit être « AUC » (aucun paiement).
Si un forfait est acheté dans un établissement non visé par les mesures sur la facturation obligatoire, mais qu’au moins un bien ou service est fourni par un exploitant visé par ces mesures, celui-ci doit produire un reçu de fermeture dont le sous-total est « 0,00 $» et dont la valeur transmise dans le champ modPai est « AUC ». La valeur affichée de chaque item peut être « 0,00 $ ». Toutefois, si l’exploitant choisit d’inscrire la valeur réelle de chaque item, le prix affiché pour l’item « FORFAIT» doit correspondre au montant négatif de la somme des items.
NOTE Chaque exploitant doit pouvoir inscrire les modes de paiement qu’il accepte. Il ne devrait donc pas avoir à inscrire « Autre »(AUT) pour un mode de paiement prévu (CRE, DEB, CHQ, CRY, etc.). Ainsi, tous les modes de paiement qu’un exploitant pourrait accepter doivent être offerts par votre SEV.

4.4.1.1.17 Références
Une « référence » est exigée pour toute transaction courante qui modifie une transaction antérieure. La référence permet d’établir le lien entre deux transactions ou plus.
Si une transaction est révisée, modifiée, corrigée, partagée, payée en plusieurs versements ou remboursée, comme lors de la production d’une note de crédit, elledoit inclure une référenceà la transaction précédente. La requête de type « transaction » doit alors inclure le champ parent refs[ ] qui contient les champs enfants noTrans, datTrans et avantTax. Si plusieurs références sont requises pour une facture, elles doivent toutes être incluses dans le champ refs [ ].
De plus, siune transaction estfinalisée, comme lors de la production d’un reçu de fermeture à lasuite d’une addition, d’une soumission ou d’une estimation, elle doit également comporter une référence à la transaction précédente.
Pour ajouter une référence, la transaction doit inclure les informations ci-dessous relatives à la transaction en référence :
• le moment (date, heure, minute et seconde) de la transaction (champ datTrans); • le numéro de la transaction (champ noTrans); • le montant avant taxes (champ avantTax).
IMPORTANT Si la transaction en référence n’est plus accessible à partir du SEV, l’utilisateur doit pouvoir saisir manuellement les informations de la transaction en référence.
